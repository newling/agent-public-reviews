## Summary

The PR registers each gfx1250 tensor DMA instruction with the race detector when it issues, using a dedicated `onAmdgpuTensorDmaIssued` hook. A load is recorded as an LDS write and a store as an LDS read, each with one TENSORcnt obligation, whether or not the transfer moves data. Completion uses the new `TENSOR` class, so partial `s_wait_tensorcnt` waits retire transfers oldest first. LDS overlap is checked with `UNORDERED`, so a transfer conflicts with any pending overlapping access, including earlier transfers from the same wave. Keeping these two orderings separate is the right design, and the new comment on `registerLdsRangeEvent` documents the split clearly. The completion observer keeps its global-request contract and now carries the issuing PC, which also fixes deferred-transfer matching in perfsim.

The latest commits also change shared detector behavior on every architecture:

- `RaceDetector::validateRead` and `validateWrite` now report the lowest byte both accesses touch (`IntervalSet::firstOverlap`), not the start of the access being checked. Before, a wide DS access was reported at its own first byte even when the overlap was elsewhere. For example, a `ds_read_b128` over bytes 0–15 racing a write to bytes 12–15 was reported at byte 0.
- Direct-to-LDS writes are now checked against pending LDS reads before they are registered, as DS writes already were. Before this change, a Direct-to-LDS write over bytes that any wave was still reading, including on gfx9, was never reported.

Both changes are correct improvements. `firstOverlap` has direct tests, and the detector and plugin tests check byte 120 in tensor reports.

## Actionable items

### Include tensor stores in the LDS barrier limitation

`emulation/rocjitsu/docs/race-detector.md:512-520` describes the LDS barrier false positive only for tensor loads. However, `tensor_dma.h` performs the descriptor-requested barrier arrival after a store as well as a load (`arrive_atomic_barrier` is called after both transfer directions). The detector does not use that arrival to retire the store's `LDS_TO_GLOBAL` read event. A wave that waits for the barrier phase and then overwrites the store's source bytes is therefore reported as racing. This was requested in an earlier round, and the thread was resolved without the change. The new tracking issue for LDS barrier cells does not mention stores either.

The ISA wording matters here. CDNA5 §10.11.3 lets any tensor operation request the arrival, but §11.2.2.1 describes "arrive when complete" only for loads. [95d5ba9e9e6](https://github.com/newling/rocm-systems/commit/95d5ba9e9e6f48e6239a4be1bd7a92ece771a4a5) adds the store case and states that store arrival has not been confirmed on hardware.

### State which counters have backpressure modeled

`emulation/rocjitsu/docs/race-detector.md:528-535` says the detector models counter-capacity backpressure "only on CDNA1 through CDNA4 and GFX11", and the limitation's title names gfx1250. In the code, `WaveRaceState::prepareForCounterIncrement` applies capacity only to the combined `vmcnt` and `lgkmcnt` counters. The generated ISA properties give those capacities to CDNA1–CDNA4 and RDNA1–RDNA3.5 (GFX10 and GFX11). It returns early for `vscnt` and `expcnt`, and for every split counter. RDNA4 has zero combined capacity, just like gfx1250. So the text omits GFX10, and it presents a gap shared with RDNA4 and other counters as specific to gfx1250.

[0b18543a2dc](https://github.com/newling/rocm-systems/commit/0b18543a2dc181aad2730723df34e13c2fad5f84) states the modeled counters and architectures, lists the unmodeled ones, and keeps the 64-transfer `tensorcnt` example.

The broader new behavior is cross-wave: another wave's pending DS read can now be overwritten by a Direct-to-LDS write, and that is now reported. ## Commentary

- Moving registration to issue time makes tensor DMA consistent with routed memory instructions. Instructions that move no data take their counter slot, a deferred transfer is registered exactly once, and perfsim's completion contract stays as it was. Nothing here needs revisiting before merge.
- The `UNORDERED` overlap check is deliberately conservative. Kernels that reuse a buffer in one wave, for example a tensor store followed by a tensor load into the same tile without `s_wait_tensorcnt`, will be reported. That is the intended behavior until the ISA states how overlapping LDS accesses are ordered. It may be worth mentioning in the gfx1250 user documentation once real kernels are run.
- The new `TENSOR` enumerator brings `MemoryCompletionClass::UNORDERED` to 7, which fills the 3-bit field in `MemoryCounterObligation`. The existing `static_assert` catches overflow, but another completion class would need a wider encoding.
- Validation scales with the number of LDS bytes in each transfer. The earlier discussion deferred this as a performance follow-up; nothing new here.
