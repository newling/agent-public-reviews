## Actionable items

### 1. Report cache notices consistently through every replay path

Locations: [tensile_host.cpp:3712](https://github.com/ROCm/rocm-libraries/blob/5a8dc64ece2472b4c15f4497a89188c82427a392/projects/hipblaslt/library/src/amd_detail/rocblaslt/src/tensile_host.cpp#L3712), and [rocblaslt_auxiliary.cpp:313](https://github.com/ROCm/rocm-libraries/blob/5a8dc64ece2472b4c15f4497a89188c82427a392/projects/hipblaslt/library/src/amd_detail/rocblaslt/src/rocblaslt_auxiliary.cpp#L313), [419](https://github.com/ROCm/rocm-libraries/blob/5a8dc64ece2472b4c15f4497a89188c82427a392/projects/hipblaslt/library/src/amd_detail/rocblaslt/src/rocblaslt_auxiliary.cpp#L419), and [629](https://github.com/ROCm/rocm-libraries/blob/5a8dc64ece2472b4c15f4497a89188c82427a392/projects/hipblaslt/library/src/amd_detail/rocblaslt/src/rocblaslt_auxiliary.cpp#L629).

The documented lifecycle and info notices depend on which entry point the application uses:

- With `HIPBLASLT_TUNING_MODE=cache` and no cache path, a null-algo-only caller skips the `tuning.reads()` block and receives no `load=no-path` explanation.
- A successful null-algo replay increments the hit counter but never reaches the cache-event logger, so info logging produces no `cache-hit` line. Its misses bypass that logger too.
- For an empty cache, both heuristic APIs print the legacy `No valid entries found in override file.` on every call. They bypass the once-per-problem cache-miss notice.

The first two cases conceal information promised by the cache interface; the third can flood an application's info log while referring to an override file that cache mode is not using.

Report a missing path before the null-algo read guard, and share the once-per-key event reporter between heuristic and direct replay paths. Keep the optimized replay tally separate so reporting does not count the lookup twice. Route empty managed-cache lookups through the same reporter while preserving the legacy override behavior.

Implemented in [406b16490c1](https://github.com/newling/rocm-libraries/commit/406b16490c1d81192db0ca96caeeb57712be6839). `NullAlgoReportsMissingCachePath` fails on the submitted head because its captured output has no `load=no-path`. `CacheInfoEventsAreReportedOnceOnBothPaths` fails because two successful null-algo calls produce zero cache-hit events, and repeated C/C++ heuristic misses produce legacy messages instead of one cache-miss event. Both regressions pass with the change.

### 2. Deduplicate invalidations by the complete saved entry identity

Locations: [UserDrivenTuningParser.cpp:123](https://github.com/ROCm/rocm-libraries/blob/5a8dc64ece2472b4c15f4497a89188c82427a392/projects/hipblaslt/library/src/amd_detail/rocblaslt/src/UserDrivenTuningParser.cpp#L123) and [272](https://github.com/ROCm/rocm-libraries/blob/5a8dc64ece2472b4c15f4497a89188c82427a392/projects/hipblaslt/library/src/amd_detail/rocblaslt/src/UserDrivenTuningParser.cpp#L272); compare [TunedEntry::sameIdentity at TuningCacheStore.hpp:307](https://github.com/ROCm/rocm-libraries/blob/5a8dc64ece2472b4c15f4497a89188c82427a392/projects/hipblaslt/library/src/amd_detail/rocblaslt/src/include/TuningCacheStore.hpp#L307).

The store deliberately preserves entries with the same problem and solution index when their saved names differ. Such rows can accumulate across rebuilds. `recordTuningInvalidation` instead deduplicates only by problem and integer index, collapsing distinct rejected entries into one.

The counterexample writes two rows at the same valid index, named `StaleKernelA` and `StaleKernelB`. Both are loaded and rejected, and default selection succeeds. The submitted code reports `loaded=2` but `invalidated=1`; the documented count of rejected entries should be 2. Repeating the lookups through both heuristics and null-algo execution leaves that undercount unchanged.

Use the store's identity definition for invalidation accounting: `(solutionIndex, kernelName, solutionName)` within each problem key. This counts each distinct stale row once while continuing to suppress repeated sightings of the same row.

Implemented in [8e32e37015c](https://github.com/newling/rocm-libraries/commit/8e32e37015c0b3c5eba8d438c70abda5104d14ca). `DistinctStaleNamesAtOneIndexCountSeparately` fails on the submitted library with actual invalidations 1 versus expected 2, and passes with the change. The existing single-stale-entry regression continues to pass.

## Commentary

The candidate cache separates two lifetimes appropriately. Resolving an index and validating its recorded name can be reused until the store generation changes. Support still depends on the individual call, including workspace and values omitted from the key, such as beta and C/D aliasing. Keeping the support check per call is essential when extending this layer with the mutable store in #12588.

The fallback probes also distinguish restoring the entire prior Tensile problem from restoring the fields changed by a support check. That allows ordinary replay to avoid copying every tensor while the alternate-math probe restores the original problem. This is a useful boundary to preserve as the downstream tuning paths grow.
