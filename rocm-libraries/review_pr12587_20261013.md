## Summary

This PR lets applications replay saved kernel choices through heuristic queries and through Tensile matmul calls that supply no algorithm. The mode and file are selected once per process. Replay validates the saved kernel name, checks support and workspace for the actual call, and leaves an explicitly supplied algorithm in control.

The separation between saved identity and per-call support is worth keeping: beta, C/D aliasing and workspace can differ without changing the stored key. The new candidate cache avoids resolving names repeatedly while retaining those support checks. Tests select a real nondefault kernel and check the computed output, so they distinguish working replay from default selection.

This review assesses the current replay layer independently of the planned downstream tuner. It adds no candidate timing loop or duplicated client measurement implementation, and its replay behavior does not depend on the future stack's extraction order. I found concrete reporting defects, but no reproduced wrong-result or wrong-kernel defect in the inspected Tensile replay paths.

### 1. Apply the diagnostic rules to direct and empty-cache calls

Locations: `projects/hipblaslt/library/src/amd_detail/rocblaslt/src/rocblaslt_auxiliary.cpp:622` (`tuning_cache_replay`), the empty-store branches at lines 313 and 419, and `projects/hipblaslt/library/src/amd_detail/rocblaslt/src/tensile_host.cpp:3712`.

The new direct path increments counters but never emits the documented info-level cache hit or miss event. A process using only `hipblasLtMatmul(..., algo=nullptr, ...)` successfully replayed a recorded kernel at log level 4, yet printed no `cache-hit` line. With cache mode enabled and no path, that same caller emitted no `load=no-path` explanation because it never enters `selectTuningFile()`. Empty-cache heuristic queries also keep printing the legacy “No valid entries found in override file” line at info level, bypassing the promised once-per-problem event rule.

Use the same event logging helper for direct replay and both heuristic paths, and announce the missing path from direct dispatch. Preserve the existing once-per-key logging sets and the separate lookup counters. Commit [e6b03ecd05fad5654c6f5068d07a2bca9700a01e](https://github.com/newling/rocm-libraries/commit/e6b03ecd05fad5654c6f5068d07a2bca9700a01e) implements this. Its fresh-process info-level test and direct missing-path test fail against the submitted library and pass with the change; the cache suite continues to pass.

### 2. Deduplicate invalidations using the same identity as stored entries

Locations: `projects/hipblaslt/library/src/amd_detail/rocblaslt/src/UserDrivenTuningParser.cpp:272` and the call in `projects/hipblaslt/library/src/amd_detail/rocblaslt/src/rocblaslt_auxiliary.cpp:226`.

The store treats index plus both optional names as an entry identity, but `recordTuningInvalidation()` deduplicates only by index. Two rows for one problem, at the same index but with different obsolete names, therefore count as two loaded entries and only one invalidation. This is a plausible file appended across rebuilds and makes the closing summary underreport the entries it rejected.

Pass the saved entry to the invalidation recorder and deduplicate by index, kernel name and solution name, matching `TunedEntry::sameIdentity()`. Commit [232b503d95a0c217d8ce2b8962b47844f53eb1da](https://github.com/newling/rocm-libraries/commit/232b503d95a0c217d8ce2b8962b47844f53eb1da) implements this. The regression writes two distinct stale identities plus a repeated row, then exercises both heuristics and direct execution twice. The submitted library reports one invalidation; the change reports two without recounting repeated lookups.

## Commentary

The submitted tests cover replay, explicit algorithms, stale names, missing files, later file creation, unsupported candidates and shape tallies. Direct replay's name cache is refreshed when store entries change, while the support helper restores the settings its check modifies. I did not find a further bounded repair in these paths. The future client-to-library move can retain this replay reader while choosing how the tuning code writes entries. Timing, candidate enumeration and winner policy belong to that later change and were not reviewed here.
