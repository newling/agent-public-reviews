## Actionable items

### Bound bias-gradient accumulation separately from the matrix product

In `projects/hipblaslt/clients/common/src/fast_check.cpp:1935`, `fast_check_bias_gradient` sums inputs into int64 without independently establishing that the GPU reduction is exact. A matrix-product bound is insufficient: when B is zero, that bound is zero even if a row of A contains `{2^24, 1, -2^24}`. Its sum in 32-bit floating-point arithmetic depends on reduction order, but the submitted helper accepts the integer sum 1 as the required answer. Large reductions can also overflow the int64 accumulator.

Commit [`7cafd4076b0`](https://github.com/newling/rocm-libraries/commit/7cafd4076b0e3e228561546772003e0a7d277827) bounds each gradient vector's absolute sum before accumulating it and refuses non-integer or inexact configurations with an explanation. The committed regression covers both gradient sources with a zero opposite operand and was reproduced before the fix. Existing small exact reductions continue to pass.

### Invalidate amax when the activation helper cannot read its inputs

In `projects/hipblaslt/clients/common/src/fast_check.cpp:1850`, the early return for an empty D or E host copy leaves the optional `amax` output unchanged. Other refusal paths assign NaN. This distinction matters to the caller at `clients/common/include/testing_matmul.hpp:6122`: it initializes the expected maximum to zero, ignores the helper's returned status in this second call, and uses NaN to recognize an unavailable expectation.

The entry initialization introduced by [`5f453a7453b`](https://github.com/newling/rocm-libraries/commit/5f453a7453bd0e495460e7b1b93733678f80c100) remains in the corrected branch. It gives the output a defined invalid value before an early return. The regression added in [`b43194c6e14`](https://github.com/newling/rocm-libraries/commit/b43194c6e14e3ae2b5db21d640d80000f8ef1fde), `FastCheckDevice_pre_checkin.activation_read_failure_invalidates_amax`, supplies an unsupported E type (`HIP_C_32F`) so the copy helper refuses it. This exercises a software refusal, without simulating a hardware malfunction.

As a negative control, removing only that entry initialization from the audited checker makes the regression fail at `std::isnan(amax)`: the output remains zero. The adjacent float-clamp regression still passes. The selected tests are reproducible with `--gtest_filter='FastCheckDevice_pre_checkin.activation_uses_the_float_clamp_argument:FastCheckDevice_pre_checkin.activation_read_failure_invalidates_amax'`; both pass with the retained initialization.

## Commentary

The earlier fractional-clamp finding was incorrect. At this PR's submitted head, `clients/common/include/hipblaslt_arguments.hpp:194` and line 195 store both activation bounds as **float**. The caller passes that already-rounded value to the kernel and to `fast_check_activation_device`; the earlier probe instead passed a double literal directly to the helper.

For the reported example, the actual float bound is `0.10000000149011612`. Multiplying it by 9 and rounding to f32 produces `0.9000000357627869` in both paths. The earlier double-literal probe produced `0.8999999761581421` and therefore did not establish a defect in the caller's behavior. Commit [`b43194c6e14`](https://github.com/newling/rocm-libraries/commit/b43194c6e14e3ae2b5db21d640d80000f8ef1fde) removes the blanket restriction from the helper and matmul preflight and replaces the misleading test with `activation_uses_the_float_clamp_argument`.

All current regressions are committed in the existing pre_checkin suite. The branch and commit dependencies are recorded above; hardware integration remains the omitted validation. The suggestion commits are published on the branch linked above.
