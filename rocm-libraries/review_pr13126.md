## Commentary

### GPU execution, ASAN and XNACK have different roles

Running a GPU correctness test and instrumenting GPU memory accesses are separate checks. A numerical test can detect a wrong matrix result. GPU ASAN can detect an invalid memory access even when that access happens not to change the result. Switching to host-only ASAN therefore reduces memory-error detection while retaining the GPU workload and its result checks.

XNACK lets the GPU retry an access after the operating system handles a recoverable page fault, such as making the requested memory available. It affects GPU execution even without GPU ASAN. Ordinary computations using explicitly allocated, accessible GPU buffers can run with XNACK disabled. ROCm's full-ASAN configuration here requires XNACK, whereas host-only ASAN can run with it enabled or disabled. Removing GPU instrumentation makes XNACK-off possible; the workflow then explicitly selects that mode.

### The sanitizer settings agree across build and execution

The [workflow](https://github.com/ROCm/rocm-libraries/blob/c92deaa96c93427a93340ae2768ce90c9eafdafa/.github/workflows/hipblaslt-asan-ci.yml#L122) changes both the global sanitizer and the explicit `amd-comgr` override, and gives both jobs a `host-asan` artifact group. The pinned TheRock module implements this with `-Xarch_host -fsanitize=address`, retaining shared sanitizer runtime linkage. This matters because changing only the runtime XNACK setting would leave incompatible full-ASAN device code in the build.

The [architecture helper](https://github.com/ROCm/rocm-libraries/blob/c92deaa96c93427a93340ae2768ce90c9eafdafa/projects/hipblaslt/cmake/tensilelite_supported_architectures.cmake#L39) gives host-only builds the regular architecture list and stops adding `xnack+`. Full ASAN and `HIPBLASLT_ENABLE_ASAN=ON` keep their previous defaults and normalization. Explicit target features remain intact at this helper boundary.

The [shared launcher](https://github.com/ROCm/rocm-libraries/blob/c92deaa96c93427a93340ae2768ce90c9eafdafa/test/therock/test_hipblaslt.py#L35) preserves an absent, disabled or enabled caller XNACK setting for host-ASAN artifacts, including debug variants. Full-ASAN artifacts still force it on. Both sanitizer modes retain `OMP_NUM_THREADS=1`; ordinary runs retain the caller's OpenMP setting. The dedicated workflow explicitly selects XNACK off both at job scope and during runtime setup. Test selection, sharding, the timeout and failure propagation remain unchanged.

No new public API, ownership rule or persistent format is introduced. The meaningful boundary cases are environment inheritance and sanitizer-dependent target defaults. The submitted PR has no dedicated regression script for these cases; its existing shared GPU workflow exercises the primary changed path, and the direct review probes cover the remaining branches. I consider that sufficient for this small conditional change, with the absence of permanent boundary tests a maintenance limitation rather than a demonstrated defect.

### The staged-consumer target is retained, but its coverage has a limit

[#11726](https://github.com/ROCm/rocm-libraries/pull/11726) moved this lane to full ASAN while repairing hipSPARSELt's import of an instrumented Python extension from staged hipBLASLt. #13126 retains the `hipSPARSELt` build target, and both products still recognize `HOST_ASAN` when constructing the Python runtime preload environment.

However, the [pinned TheRock architecture configuration](https://github.com/ROCm/TheRock/blob/3c4ec014374d4d32243334ef229093fe7b38c5b2/cmake/therock_amdgpu_targets.cmake#L86) excludes gfx90a from hipSPARSELt. The current build log confirms that exclusion. With no remaining GPU target, [hipSPARSELt disables its device library](https://github.com/ROCm/rocm-libraries/blob/c92deaa96c93427a93340ae2768ce90c9eafdafa/projects/hipsparselt/CMakeLists.txt#L94), bypassing the Python code-generation path. Thus, the successful consumer build is not evidence that the exact historical import regression ran. This limitation exists before #13126 and does not make its sanitizer change incorrect. Dedicated validation of that consumer path needs a supported hipSPARSELt architecture or a targeted staged-import check.

### The cause of the hangs remains unresolved

The observed full-ASAN failures are predominantly hangs and timeouts without an ASAN memory-error report. In the [controlled runner comparison](https://github.com/ROCm/rocm-libraries/actions/runs/36777979287), the same compiled artifact hangs on the original pool and passes on the alternate pool. Captured startup stacks place the CPU in a ROCm runtime wait for GPU code-cache invalidation during the first GPU-buffer clear. This identifies where progress stops, not which component is responsible.

There is no demonstrated CPU buffer overflow or use-after-free behind these hangs. Host memory management, the GPU driver, firmware, GPU state or a timing-sensitive software bug could still be involved. Containers do not equalize the host kernel, kernel GPU driver or device state. Passing host-only ASAN shows that CPU instrumentation can run in the tested configuration, but #13126 changes both GPU instrumentation and XNACK together. Its successful run cannot determine whether either change alone would suffice, or why the pools behave differently.

The hang remains tracked in [libraries #12727](https://github.com/ROCm/rocm-libraries/issues/12727) and [TheRock-Infra #978](https://github.com/ROCm/TheRock-Infra/issues/978), both still open. The latter's investigation requests kernel/crash evidence to establish whether these failures share a cause. Keep that investigation open; this PR does not establish a root-cause repair.

There is no configured replacement gfx90a full-ASAN runtime lane in the inspected configuration. Merged [TheRock #8507](https://github.com/ROCm/TheRock/pull/8507) adds a gfx90a ASAN-debug nightly **build**, deliberately without a test runner. The general ASAN summary is also insufficient evidence: ordinary host-ASAN PR tests are disabled by the inspected TheRock policy, with [#8455](https://github.com/ROCm/TheRock/pull/8455) still open to change that. Other architectures' ASAN sandboxes do not establish gfx90a runtime coverage.

[#12813](https://github.com/ROCm/rocm-libraries/pull/12813) offers a different mitigation, supported by the identical-artifact comparison and successful full-ASAN workflows: preserve the existing sanitizer coverage and move execution to another runner pool.

I would approve #13126 for routine presubmit checks and hold #12813 pending the decision about retaining full gfx90a device checking. Its runner selection remains a candidate for a separate full-ASAN lane. If that coverage is dropped, #12813 is superseded for this workflow; that does not invalidate its workaround evidence. Neither approach has established a root cause or a long-term reliability rate.

The placement and ownership of full-ASAN runtime coverage need an explicit follow-up decision, but I would not require this PR's author to solve the infrastructure hang or introduce another lane before approval.
