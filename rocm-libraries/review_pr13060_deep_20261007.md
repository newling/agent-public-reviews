## Actionable items

### Do not infer that a register pair stopped holding an address from its opcode

At `projects/hipblaslt/tensilelite/Tensile/Utilities/address_carry_lint.py:447`, `updates_bit_op_result()` and `high_holds_integer()` skip the carry check based on the preceding opcode. Neither establishes that the pair is no longer a pointer. Incrementing its high word is a valid address update by a multiple of 4 GiB; XORing the low word with zero preserves it.

For example, the submitted linter reports no finding for:

```asm
s_mov_b32 s8, 0xfffffff0
s_mov_b32 s9, 0x1234
s_add_u32 s9, s9, 1
s_add_u32 s8, s8, 64
s_load_dword s0, s[8:9], 0
```

The intended address after both updates is `0x123600000030`; the load uses `0x123500000030`. Replacing the high-word update with `s_xor_b32 s8, s8, 0` also hides the missing carry, and the analogous vector XOR case is missed. All three matching controls become correct by carrying into the high word before the load, and remain warning-free.

Commit [b8a15f0b12ce](https://github.com/newling/rocm-libraries/commit/b8a15f0b12cedd8e4b0128b1fecb9e1a51b5a04b) removes both opcode-based exemptions and commits these scalar/vector regressions. It retains the motivating register-reuse fixtures and documents their conservative warnings. Reducing those warnings safely requires establishing that an address-use path is infeasible or that the value has been redefined; an arithmetic-opcode allow-list cannot establish either fact. This bounded fix intentionally accepts that warning-volume tradeoff and does not add a predicate solver. The reproducer source is committed.
