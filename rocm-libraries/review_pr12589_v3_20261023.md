## Summary

This change saves the best measured candidate when a tuning budget ends early, records how much searching and measurement produced it, and uses that information to decide whether a later process has reason to search again. It also defines which saved result takes precedence when a shape has several rows.

Two choices are worth retaining: a partial result is saved only after measuring the kernel the call would otherwise use, and retuning applies the same name and support checks as replay. Strict version-2 parsing also avoids turning a damaged partial row into a completed result. The remaining problems are in how repeated rows are coalesced; the documented precedence rules need to hold when a search selects an algorithm already present in the file.

## Actionable items

### 1. Refresh the winner's position as well as its metadata

Location: [`TuningCacheStore.hpp:651–656`](https://github.com/ROCm/rocm-libraries/blob/1804c099346b49c853a8d023b2e0ef848aab00de/projects/hipblaslt/library/src/amd_detail/rocblaslt/src/include/TuningCacheStore.hpp#L651-L656), together with `find()` at lines 509–515.

`addTo()` overwrites an existing algorithm's row in place, while `find()` uses reverse insertion order to implement newest-first preference. With completed winners A, B, then A again, the map still returns B first. Loading those three appended rows produces the same wrong order. The row for the latest A search can also make `needsRetune()` return false, leaving the older B winner in use indefinitely despite the successful new search.

Move a refreshed versioned entry to the end of its equal-key range so both live updates and reloads treat it as the latest result. Keep legacy rows in their historical file order.

Implemented in [169050303c4](https://github.com/newling/rocm-libraries/commit/169050303c4c8032a1e960bfe2c31fe99ec852db). `TuningStore.RefreshedWinnerIsNewestWithinItsGroup` checks the A/B/A sequence for completed and partial rows, both directly and after loading the file, and checks that legacy preference does not change. It fails on submitted code and passes with the fix.

### 2. Retain completed and partial results for the same kernel

Location: [`TuningCacheStore.hpp:651–654`](https://github.com/ROCm/rocm-libraries/blob/1804c099346b49c853a8d023b2e0ef848aab00de/projects/hipblaslt/library/src/amd_detail/rocblaslt/src/include/TuningCacheStore.hpp#L651-L654), reached by the new `cache.addIfAbsent(key, winner)` call in [`tensile_host.cpp:5776`](https://github.com/ROCm/rocm-libraries/blob/1804c099346b49c853a8d023b2e0ef848aab00de/projects/hipblaslt/library/src/amd_detail/rocblaslt/src/tensile_host.cpp#L5776).

The refresh identity contains only the solution index and names. If a completed two-candidate search selects A and a later, wider search stops early with A again, the partial row overwrites the completed row, including its completion flag and search metadata. Complete-first ordering cannot preserve a result that the map has discarded. A later narrow run unnecessarily retunes; if an older completed B row also exists, replay can switch back to B. The file loader performs the same coalescing, so restarting does not recover the completed A result.

Retain completed and partial results separately for a versioned algorithm identity. Keeping the partial metadata matters too: it suppresses another identical budget-limited search of the wider candidate set.

Implemented in [28fd850d13b](https://github.com/newling/rocm-libraries/commit/28fd850d13b5ee7e81faccc23574948f76f6f56a). `TuningStore.PartialRefreshKeepsTheSameKernelsCompletedSearch` checks live and reloaded state, both search-coverage decisions, and preference against an older completed competitor. The original counterexample fails on submitted code; the final store suite passes. `RefreshingAnEntryMovesTheGeneration` continues to test a metadata refresh within one completion group.
